## 1. The three-source model

Functional completeness must consume the repository's existing systems instead of duplicating them.

```text
docs/codebase/
    "What does Vortex actually do today?"
    generated by /document-vortex
            |
            v
docs/habbo-specs/
    "What do we know about the target client / Habbo protocol?"
    generated and queried by habbo-spec
            |
            v
docs/completeness/
    "What is the gap between the target surface and Vortex?"
    driven by /vortex-completeness
```

### Authority by question

| Question | Primary source |
|---|---|
| Current ownership, runtime flow, persistence, project boundaries | `docs/codebase/` + current code |
| Intended repository invariants | `AGENTS.md`, `CONTEXT.md`, `CLAUDE.md`, accepted ADRs |
| Packet layout / client-visible protocol evidence | `docs/habbo-specs/` + target client source |
| Official runtime behaviour | capture or client-mandated evidence when available |
| What is missing | `docs/completeness/generated/` |
| Historical intent | audits/roadmaps only as orientation |

`docs/codebase/` is authoritative for **what the documented commit does**, not for a newer HEAD.
`docs/habbo-specs/` is authoritative for **what is known**, including unknowns; Vortex implementation
is never promoted into official Habbo truth.

## 2. Documentation freshness gate

Before completeness analysis:

1. read `docs/codebase/.documentation-state.json`;
2. compare `documentedCommit` to `HEAD`;
3. inspect the diff;
4. if implementation paths relevant to the requested domain changed, update the codebase documentation;
5. if only documentation/skill files changed, do not regenerate the entire codebase docs just to match SHA.

Canonical command/workflow:

```text
/document-vortex update
```

A completeness agent must **consume** `document-vortex`; it must not implement a second architecture scanner.

After a feature implementation changes documented runtime behaviour, run `/document-vortex update`
before closing the slice.

## 4. Primary obligation surface

For FC-1:

```csharp
var targetClients = world.Clients
    .Where(c =>
        c.Authority == EvidenceAuthority.ClientCode &&
        c.TargetsSameRevision);

var incomingObligations = targetClients
    .SelectMany(c => c.Packets)
    .Where(p =>
        p.Direction == PacketDirection.Incoming &&
        p.HeaderId is not null)
    .GroupBy(p => p.Canonical, StringComparer.Ordinal)
    .Select(g => g.First());
```

Rules:

- same-revision official client only;
- `HeaderId == null` → `UNRESOLVED_SURFACE`, never silently excluded as success;
- older official clients remain evidence, not denominator;
- duplicate canonical packet names become one obligation;
- an obligation missing from Vortex stays visible even if no `FeatureSpec` exists;
- `NOT_APPLICABLE` requires an explicit decision with evidence.

## 6. Canonical statuses

### `MISSING`

The target obligation is resolved in the client but Vortex has no usable protocol entry path.

Examples:

- no `PacketSpec`;
- `MappedInVortex == false`;
- no `VortexHandler`.

### `PARTIAL`

The entry path exists but the functional slice is not proven complete.

Examples:

- handler exists but is stub/no-op;
- no meaningful flow beyond handler;
- required domain effect absent;
- required response absent/unresolved;
- required persistence absent according to the actual owner semantics;
- known user-visible gap remains;
- the path is explicitly best-effort while the client requires a result.

### `IMPLEMENTED`

A meaningful Vortex path exists and static/runtime documentation does not expose an obvious missing step.

`IMPLEMENTED` means **Vortex has code**. It does not mean Habbo behaviour is officially verified.

### `COMPLETE`

Only after verification evidence exists.

Minimum expectation:

- implementation is meaningful;
- correct target-revision wire shape for the exercised path;
- tests appropriate to risk;
- no critical unknown that blocks the behaviour being claimed;
- no unresolved conflict that changes the claimed behaviour;
- client/capture/client-mandated evidence where official behaviour matters.

FC-1 may conservatively stop at `IMPLEMENTED`. It must not mass-promote static paths to `COMPLETE`.

### `UNKNOWN`

The available sources are insufficient to classify the obligation safely.

### `NOT_APPLICABLE`

Explicit exclusion only. Requires:

- reason;
- evidence;
- decision id;
- commit/revision context.

Never use N/A to improve a percentage.

### `UNRESOLVED_SURFACE`

The target client contains a candidate surface that the analyzer cannot bind sufficiently to score.
It remains visible outside the denominator until resolved.

## 9. Verification records

Manual verification is allowed only to record evidence, not to override missing implementation.

Use `verification.yaml`.

Example:

```yaml
version: 1

obligations:
  incoming/MoveObject:
    verified_at_commit: abc123
    tests:
      - Vortex.Rooms.Tests/...
    protocol:
      - docs/habbo-specs/packets/incoming/...
    codebase_docs:
      - docs/codebase/04-rooms/furniture.md
    notes:
      - "Target client parser and Vortex serializer path checked."
```

A verification record may promote an otherwise `IMPLEMENTED` obligation toward `COMPLETE`.
It must never turn `MISSING` into `COMPLETE`.

## 11. Specialized non-packet inventories

Packet completeness is first, not the whole product.

### Furniture

Surface of truth:

```text
FurnitureDefinition.logic values actually used
       ↓
RoomObjectLogicProvider resolution
       ↓
specialized behaviour / intentional family fallback
       ↓
number of impacted definitions
```

Prioritize by impacted definitions and player reachability.

A fallback is not automatically a bug. An accidental fallback affecting hundreds of definitions is.

### Wired

Do not re-audit the V4 engine.

Inventory box/types:

```text
client/configurable wired type
       ↓
logic registration
       ↓
save/load parameters
       ↓
runtime execution
       ↓
FakeWiredRoomHost tests
```

### Outgoing-only

The target client contains server→client packets that are not independently "features."

Measure:

1. serializer/header compatibility when Vortex emits the message;
2. whether a reachable feature actually requires the message.

Do not classify an unused outgoing as missing without a feature that needs it.

## 14. Risk-based verification

| Type | Minimum verification direction |
|---|---|
| Stateless read/response | packet contract + unit/integration |
| Room mutation | room/grain/host test + wire path |
| Furniture behaviour | logic test + room path + definition binding |
| Wired box | fake host behavioral parity test |
| Economy/value movement | operation-id/idempotence/fault-injection as applicable |
| Permissions/moderation | authorization/policy matrix + audit |
| Concurrency/retry | deterministic retry/interleaving test |
| Wire ordering | capture when official order matters |

The existence of a test with a similar class name is not evidence. Record the exact test path/property.

## 15. Priority model

### P0

- client-visible and `MISSING`;
- value-loss/value-duplication/security/moderation correctness.

### P1

- client-visible `PARTIAL`;
- high-usage furniture families with accidental fallback;
- broken reachable dialogs/workflows.

### P2

- reachability unknown;
- client surface present but optional/dead-code status unproven.

### P3

- old revision only;
- optional/server-push surface without a demonstrated reachable feature.

Do not prioritize by packet count alone.

## 17. Anti-score-gaming rules

Rejected changes:

- adding an empty handler just to become mapped;
- marking N/A because implementation is difficult;
- deleting a target-client obligation;
- lowering unknown/conflict severity without evidence;
- adding a serializer never mapped or never emitted and calling the feature done;
- relying on a reference emulator as official truth;
- changing architecture purely to improve a completeness score;
- marking a path complete because "it compiles."

## 20. Acceptance criteria

Phase 2 infrastructure is successful when:

1. the target-client denominator is reproducible;
2. code absent from Vortex cannot disappear from the report;
3. every scored obligation has provenance;
4. N/A decisions require evidence;
5. `IMPLEMENTED` and `COMPLETE` are not conflated;
6. codebase docs are consulted for real ownership/persistence semantics;
7. Habbo specs remain the protocol evidence source;
8. a feature PR automatically changes the generated matrix for a concrete reason;
9. documentation is refreshed after behavior changes;
10. an agent can answer “what is the next highest-value missing feature?” without re-auditing the architecture.
