# Habbo Specs

Machine-generated behavioural specs for the Habbo protocol, built from evidence and regenerated by
`habbo-spec`. Nothing in this tree is hand-authored documentation, and nothing in it is a guess.

```bash
dotnet run --project Vortex.Specs.Cli -- bootstrap        # regenerate everything, print a report
dotnet run --project Vortex.Specs.Cli -- analyze room.move_floor_item_in_room
dotnet run --project Vortex.Specs.Cli -- validate
dotnet run --project Vortex.Specs.Cli -- conflicts
dotnet run --project Vortex.Specs.Cli -- unknowns --severity critical
```

## The problem this exists for

We do not have Habbo's server. We can read what a packet looks like — the official client's own
composers and parsers say so — and we can read what several other people's servers do with it. What
none of that tells us is what Habbo's server does: which requests it refuses, what it sends back when
it refuses, in what order, and to whom.

So the tree separates two things that are easy to conflate and expensive to confuse:

- **`observed_in`** — what an implementation does. This emulator moving furniture a certain way is a
  fact about this emulator.
- **`official_behavior`** — what Habbo does. `unknown` until a capture says otherwise, and a capture
  is the only thing that can say.

> Existing emulator behaviour is evidence, not authority.
> Reference emulator behaviour is evidence, not authority.
> Unknown official behaviour must remain explicitly unknown.

## Layout

| Path | Holds |
|---|---|
| `packets/incoming/<domain>/` | Client-to-server messages: fields, types, per-source layouts |
| `packets/outgoing/<domain>/` | Server-to-client messages, same shape |
| `features/<domain>/` | Behaviour: trigger, flow, guards, state changes, what goes out to whom |
| `scenarios/<domain>/` | One file per feature: the happy path plus one scenario per observed guard |
| `conflicts/<kind>/` | Where sources disagree. Never arbitrated |
| `unknowns/<severity>/` | Questions the sources do not answer, with what would close each one |
| `revisions/` | Per-source header tables. The **only** place numeric ids appear |
| `evidence/client/`, `evidence/references/` | What each reader managed to extract |
| `evidence/captures/` | Captures, and the observations they yield. See its README for the format |
| `REPORT.md` | The last run: counts, confidence mix, what the readers could not resolve |

## Reading a spec

Every file has the same envelope:

```yaml
spec: packet
spec_version: 1
generated_digest: "sha256:..."
generated:      # the tool's. Rewritten on every scan.
  ...
verified:       # yours. Backed by evidence. Never touched by the tool.
manual:         # yours. Notes and context. Never touched by the tool.
```

Edit `verified:` and `manual:` freely — they survive regeneration verbatim. An edit inside
`generated:` is detected by the digest and **blocks** the next regeneration rather than being
reverted: the new version lands beside the file as `<name>.yaml.regenerated.yaml` for you to
reconcile, and `habbo-spec validate` warns until you do.

## Confidence

Attached to every claim, and never higher than the evidence behind it.

| Level | Means |
|---|---|
| `confirmed` | Two or more official-grade sources agree |
| `capture_confirmed` | A capture of an official Habbo server shows it |
| `client_confirmed` | The official client's own code fixes it |
| `multi_reference_confirmed` | Two or more independent non-Vortex implementations agree |
| `reference_observed` | One third-party emulator does it |
| `implementation_observed` | This emulator does it. Says nothing about Habbo |
| `inferred` | Derived from the above rather than observed |
| `assumed` | A guess, recorded so it can be argued with |
| `unknown` | Nothing supports a value either way |
| `conflicting` | Sources disagree and no rule here may pick a winner |

Two rules do most of the work. Vortex agreeing with a reference emulator is **not** two independent
observations — this emulator was written partly by reading those. And no number of reimplementations
agreeing with each other reaches `confirmed`; that needs official-grade evidence.

A field nobody names comes out as `unknown_3` with `name_is_placeholder: true`. That is the correct
output: a placeholder invites the next scan to fill it in, where an invented name looks like
knowledge and never gets revisited.

## Header ids

Symbolic names everywhere; ids only in `revisions/`. The same message is 1482 in the client this
emulator targets, 2828 in Nitro's table and 248 in Arcturus's, and all three are right for their own
build. Ids are only ever compared between tables that target the *same* build — `habbo-spec headers`
says which those are.

## Adding evidence

The fastest way to make this tree more useful is a capture. Drop it in `evidence/captures/` (format
in that directory's README) and re-run `bootstrap`: every scenario it touches stops being `unknown`.
